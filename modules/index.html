    System Modules¶

    Module Breakdown¶

    Users Module¶

    User

    • Custom user model based on AbstractUser
    • Fields:
    • email (Unique, Login Field)
    • username (Unique)
    • role (Enum: SUPER_ADMIN, ADMIN, GAMER, Default: GAMER)
    • tenant (FK → Tenant, Nullable)
    • is_verified (Boolean, Default: False)
    • is_active (Boolean, Default: True)
    • Key Logic:
    • Soft deletion support (overrides delete to set is_active=False and deleted_at)
    • Indexes on (tenant, role) and (email, is_verified)

    Tenants Module¶

    Tenant

    • Represents the organization/account context
    • Fields:
    • name (Char)
    • status (Enum: ACTIVE, INACTIVE, PREMIUM, Default: ACTIVE)
    • Key Logic:
    • Central entity for multi-tenancy rules

    Tenant Games Module¶

    TenantGame

    • Links a Tenant to a Catalog Game (Availability)
    • Fields:
    • tenant (FK → Tenant)
    • game (FK → Catalog Game)
    • Key Logic:
    • Unique constraint on (tenant, game) (where active) implies a tenant cannot have duplicate entries for the same game.
    • Soft deletion support.

    Games Module (Catalog)¶

    Game

    • Represents a global/catalog game entry
    • Fields:
    • title (Char)
    • description (Text, Optional)
    • release_date (Date, Optional)
    • genre (FK → Genre)
    • platforms (M2M → Platform)

    Genres Module¶

    Genre

    • Reference data for categorizing games
    • Fields:
    • name (Char)

    Platforms Module¶

    Platform

    • Reference data for gaming platforms
    • Fields:
    • name (Char)

    User Games Module¶

    UserGame

    • Represents a specific user's instance/progress of a game
    • Fields:
    • user (FK → User)
    • tenant_game (FK → TenantGame)
    • platform (FK → Platform)
    • status (Enum: WISHLIST, PLAYING, COMPLETED, DROPPED, Default: WISHLIST)
    • tenant (FK → Tenant)
    • hours_played (PositiveInt, Optional)
    • personal_rating (PositiveSmallInt, Optional)
    • started_on (Date, Optional)
    • completed_on (Date, Optional)
    • Key Logic:
    • Indexes on (user, status), created_at, (user, tenant).

    UserGameNote

    • Notes attached to a user game
    • Fields:
    • user_game (FK → UserGame)
    • note (Text)
    • tenant (FK → Tenant)

    Payments Module¶

    Payment

    • Tracks individual payment transactions via Razorpay
    • Fields:
    • tenant (FK → Tenant)
    • admin (FK → User)
    • razorpay_order_id (Char, Unique)
    • razorpay_payment_id (Char, Nullable)
    • razorpay_signature (Char, Nullable)
    • amount (Int, in paise)
    • status (Enum: CREATED, AUTHORIZED, PAID, VERIFIED, ACTIVATED, FAILED, REFUNDED, CANCELLED)
    • verified_at (DateTime, Optional)
    • activated_at (DateTime, Optional)
    • error_message (Text, Optional)
    • metadata (JSON)
    • Key Logic:
    • State transitions validation.

    Subscription

    • Tracks tenant subscription status
    • Fields:
    • tenant (OneToOne → Tenant)
    • payment (FK → Payment, Nullable, tracks activation payment)
    • status (Enum: NONE, PENDING, ACTIVE, EXPIRED, Default: NONE)
    • activated_at (DateTime, Optional)
    • deactivated_at (DateTime, Optional)
    • Key Logic:
    • Designed for lifetime activation (One subscription per tenant).

    WebhookEvent

    • Logs raw webhook requests for audit
    • Fields:
    • event_id (Char, Unique)
    • event_type (Char)
    • payload (JSON)
    • raw_body (Text)
    • status (Enum: PENDING, PROCESSING, PROCESSED, FAILED, Default: PENDING)
    • error_message (Text, Optional)
    • retry_count (Int)
    • processed_at (DateTime, Optional)

    Database Design¶

    Key Design Principles¶

    • Normalization: Catalog data (Game, Genre, Platform) is separated from Tenant and User data.
    • Multi-tenancy: Almost all interaction models (User, UserGame, Payment, TenantGame) link explicitly to Tenant.
    • Soft Deletion: Core models inherit from BaseModel which provides id, created_at, updated_at and deleted_at.
    • Enums: Used strictly for Statuses and Roles to enforce business logic.

    Indexes & Constraints Overview¶

    Uniqueness:¶

    • users.email
    • users.username
    • tenant_games(tenant, game) (Active records)
    • payments.razorpay_order_id
    • webhook_events.event_id

    Performance Indexes:¶

    • users(tenant, role)
    • user_games(user, status)
    • payments(tenant, status)
    • webhook_events(status, created_at)
